## API documentation (Swagger UI)

The API ships with an OpenAPI 3 specification generated by
[`@nestjs/swagger`](https://docs.nestjs.com/openapi). The setup lives in
[`src/main.ts`](src/main.ts):

- **Swagger UI** – <http://localhost:3001/docs>
- **OpenAPI JSON** – <http://localhost:3001/docs-json>
- **OpenAPI YAML** – <http://localhost:3001/docs-yaml>

Authentication is described with a bearer (`access-token`) security scheme, so
protected endpoints can be called straight from the UI: click **Authorize**,
paste the `accessToken` returned by `POST /auth/login` and every secured route
will send the `Authorization: Bearer <token>` header for you.

Every controller is grouped in a tag (`auth`, `categories`, `products`,
`inventory`, `cart`, `checkout`, `orders`, `payments`, `roles`, `users`,
`discounts`, `reports`) and every request body is described by a DTO with
`@ApiProperty` metadata, so the UI renders example payloads, required fields and
validation constraints.

The `@nestjs/swagger` CLI plugin is enabled in [`nest-cli.json`](nest-cli.json)
so DTO metadata is generated automatically at build time.

## Email verification with a one-time code (OTP)

New accounts are created with the `PENDING_VERIFICATION` status and cannot log
in until their email address is confirmed with a one-time code.

| Method | Route                             | Description                                        |
| ------ | --------------------------------- | -------------------------------------------------- |
| `POST` | `/auth/register`                  | Creates the account and sends the first code        |
| `POST` | `/auth/email/verification-code`   | Sends (or re-sends) a one-time code by email        |
| `POST` | `/auth/email/verify`              | Validates the code and activates the account        |
| `POST` | `/auth/login`                     | Rejects unverified accounts with `403 Forbidden`    |

Example flow:

```bash
# 1. Register — a code is emailed automatically
curl -X POST http://localhost:3001/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"customer@example.com","password":"Str0ngPassword!","firstName":"Jane","lastName":"Doe"}'

# 2. (optional) request a new code
curl -X POST http://localhost:3001/auth/email/verification-code \
  -H "Content-Type: application/json" \
  -d '{"email":"customer@example.com"}'

# 3. Submit the code received by email
curl -X POST http://localhost:3001/auth/email/verify \
  -H "Content-Type: application/json" \
  -d '{"email":"customer@example.com","code":"123456"}'
```

Security rules applied by [`src/auth/verification.service.ts`](src/auth/verification.service.ts):

- the plain code is never stored, only a bcrypt hash of it;
- a code is single use, expires after `OTP_EXPIRES_IN_MINUTES` (default 10) and
  can be retried at most `OTP_MAX_ATTEMPTS` times (default 5);
- requesting a new code invalidates the previous one and is rate limited by
  `OTP_RESEND_COOLDOWN_SECONDS` (default 60, answered with `429 Too Many Requests`);
- verifying the email sets `User.emailVerified` and moves the account from
  `PENDING_VERIFICATION` to `ACTIVE`.

Delivery is handled by [`src/mail/mail.service.ts`](src/mail/mail.service.ts)
(nodemailer). Configure it with the `MAIL_*` variables (`MAIL_HOST`,
`MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM_ADDRESS`,
`MAIL_FROM_NAME`); the `SMTP_*` aliases are also accepted. When no SMTP host is
configured the messages are only written to the application log, and
`MAIL_TRANSPORT=json` captures the emails instead of sending them.

## "Keep me signed in" (remember me)

`POST /auth/login` accepts an optional `rememberMe` flag. It drives the lifetime
of the issued tokens, so the admin panel can offer a "Keep me signed in"
checkbox:

| Field        | Access token                       | Refresh token                        |
| ------------ | ---------------------------------- | ------------------------------------ |
| `rememberMe: false` (default) | `JWT_ACCESS_EXPIRATION` (default `15m`) | `JWT_REFRESH_EXPIRATION` (default `7d`) |
| `rememberMe: true`  | `JWT_REMEMBER_ME_EXPIRATION` (default `30d`) | `JWT_REMEMBER_ME_REFRESH_EXPIRATION` (default `90d`) |

```bash
curl -X POST http://localhost:3001/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"Str0ngPassword!","rememberMe":true}'
```

The response contains the tokens plus `rememberMe` and `expiresInMs` (the
lifetime of the access token in milliseconds). The refresh token carries the
`rememberMe` flag, so `POST /auth/refresh` renews a remembered session with the
same long lifetime and a normal session with the short one. The stored
`Session` row expires together with the access token.

The admin panel keeps the session in `localStorage` when the box is ticked
(the session survives a browser restart) and in `sessionStorage` otherwise (the
session ends with the browser tab).

## Roles and user assignments

Roles are managed by the [`src/roles`](src/roles) module and the users by the
[`src/users`](src/users) module. The role names are free-form (they used to be
a fixed `RoleName` enum), so custom roles such as `EDITOR` or `SUPPORT` can be
created through the API. The names are normalized to upper case and must be
unique.

| Method   | Route                        | Access        | Description                                     |
| -------- | ---------------------------- | ------------- | ----------------------------------------------- |
| `GET`    | `/roles`                     | authenticated | Lists the roles (`?includeInactive=true` too)    |
| `GET`    | `/roles/name/:name`          | authenticated | Gets a role by its name                         |
| `GET`    | `/roles/:id`                 | authenticated | Gets a role with its assigned users             |
| `POST`   | `/roles`                     | `ADMIN`       | Creates a role                                  |
| `POST`   | `/roles/seed`                | `ADMIN`       | Creates the `ADMIN`, `STAFF` and `CUSTOMER` roles |
| `PATCH`  | `/roles/:id`                 | `ADMIN`       | Renames or updates a role                       |
| `DELETE` | `/roles/:id`                 | `ADMIN`       | Deletes a role (`?force=true` also drops users) |
| `GET`    | `/roles/:id/users`           | `ADMIN`, `STAFF` | Lists the users holding a role               |
| `POST`   | `/roles/:id/users`           | `ADMIN`       | Assigns the role to a user                      |
| `DELETE` | `/roles/:id/users/:userId`   | `ADMIN`       | Revokes the role from a user                    |
| `GET`    | `/users`                     | `ADMIN`, `STAFF` | Lists the users with their roles             |
| `GET`    | `/users/:id`                 | `ADMIN`, `STAFF` | Gets a user with its roles                   |
| `GET`    | `/users/:id/roles`           | `ADMIN`, `STAFF` | Lists the roles of a user                    |
| `POST`   | `/users/:id/roles`           | `ADMIN`       | Assigns a role to a user                        |
| `DELETE` | `/users/:id/roles/:roleId`   | `ADMIN`       | Revokes a role from a user                      |

Example:

```bash
# Create a role
curl -X POST http://localhost:3001/roles \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"EDITOR","description":"Can edit the catalog"}'

# Assign it to a user (by id or by email)
curl -X POST http://localhost:3001/roles/$ROLE_ID/users \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"userEmail":"customer@example.com"}'

# List the roles of a user
curl http://localhost:3001/users/$USER_ID/roles \
  -H "Authorization: Bearer $TOKEN"
```

Rules applied by [`src/roles/roles.service.ts`](src/roles/roles.service.ts):

- the default roles `ADMIN`, `STAFF` and `CUSTOMER` are created when the API
  starts, so the `@Roles()` decorator of the existing endpoints always matches;
- a new registration always receives the `CUSTOMER` role;
- assigning a role twice is idempotent, the existing assignment is returned;
- a role that is still assigned to users is only deleted with `?force=true`;
- the role of the last administrator cannot be revoked.

The administration panel ships a **Roles** page (`/roles` in the `admin` app)
that lists the roles, creates, renames and deletes them and assigns or revokes
a role for any user.

## Business reports

The [`src/reports`](src/reports) module aggregates the orders of a period so the
administration panel does not have to download every order to sum it up.

| Method | Route      | Access          | Description                             |
| ------ | ---------- | --------------- | --------------------------------------- |
| `GET`  | `/reports` | `ADMIN`, `STAFF` | Aggregated report of a period          |

Query parameters:

| Parameter     | Type                                   | Default        | Description                                   |
| ------------- | -------------------------------------- | -------------- | --------------------------------------------- |
| `from`        | ISO 8601 date                         | 30 days ago    | First day of the window (the whole day)       |
| `to`          | ISO 8601 date                         | today          | Last day of the window (the whole day)        |
| `granularity` | `day`, `week` or `month`               | `day`          | Bucket size of the sales over time series     |
| `limit`       | number (1 – 50)                       | `10`           | Size of the top products / top customers lists |

```bash
curl "http://localhost:3001/reports?from=2026-09-01&to=2026-09-30&granularity=week" \
  -H "Authorization: Bearer $TOKEN"
```

The response contains:

- `period` – the resolved window and its granularity;
- `summary` – revenue, order counts, average order value, items sold, customers
  and the variation against the previous period of the same length;
- `salesOverTime` – one entry per bucket, empty buckets included;
- `orderStatusBreakdown` – the orders of the window per status;
- `topProducts` and `topCustomers` – the best performers of the period.

Rules applied by [`src/reports/reports.service.ts`](src/reports/reports.service.ts):

- the cancelled and the refunded orders are excluded from the revenue, the
  items sold and the rankings (they are still counted in `grossRevenue` and in
  the order counters);
- every amount is expressed in minor units (cents), like the rest of the API;
- the window cannot be inverted and cannot exceed 366 days.

The administration panel ships a **Reports** page (`/reports` in the `admin`
app) that renders the report, lets you pick the period and exports the sales
over time series as a CSV file.
